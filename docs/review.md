# Review 准则

仅在执行代码 Review 时使用本文。目标是确认改动正确、安全，并以最小充分方式满足需求。

## 核心原则

- 完整满足已确认需求，不增加没有需求依据的功能、配置、接口、抽象、依赖、持久化数据或后台任务。
- 按[架构与代码导航](architecture.md)确认职责归属，优先复用现有模块、接口、模型和流程。
- Review 只报告有明确触发条件和实际影响的问题，不把个人风格偏好当作缺陷。
- 不把与当前需求无关的重构、格式化或依赖升级混入改动。

## 检查清单

### 范围与架构

- 新增内容是否都能对应到明确需求，是否遗漏已确认的行为或失败路径。
- 业务逻辑是否仍由 `core` 编排，适配层是否保持轻量，基础设施是否没有反向依赖业务层。
- 是否出现重复实现、绕过现有流程的旁路，或本可放入现有模块的新模块。

### 正确性与安全

- 正常、空值、边界、重复调用和部分失败时，状态与返回结果是否正确。
- 重试和批处理是否幂等，是否会重复发送种子、创建任务或写入文件。
- goroutine、锁、事务、文件、响应体和数据库 rows 是否在所有路径正确结束或释放。
- 日志、API、示例和错误信息是否泄漏 Cookie、密码、Token 或其他敏感数据。
- 文件路径、URL、SQL 动态部分和外部响应是否经过必要校验。

### 数据与性能

- 业务事实、派生索引和本地文件是否遵循[存储与数据库](storage.md)的边界。
- qB 进度、速度、ETA 和实时状态不得持久化；稳定字段无变化时不应重复写库。
- 批量写入是否使用事务，是否引入逐行提交、N+1 查询、无界扫描或不必要的索引写放大。
- schema 是否能独立初始化，不能依赖以后会删除的迁移补丁。

### 兼容与验证

- 是否意外改变已有 API、配置默认值、数据库语义、文件布局或调度行为。
- 前后端类型及相关 API、配置、存储文档是否与实现一致。
- 测试和检查是否真正覆盖改动；fake 测试不能当作真实站点或 qB 验证。
- 未执行的检查、缺失环境和残余风险是否明确说明。

## Review 输出

发现按严重程度排列：

- `P0`：数据损坏、凭据泄漏、严重安全问题或应用不可用。
- `P1`：主要功能错误、兼容性破坏、重复任务或持续资源问题。
- `P2`：特定条件下的正确性、性能或维护问题。

每条发现说明代码位置、触发条件、实际影响和最小修正方向。没有发现问题时，直接说明未发现问题及尚未完成的验证。
