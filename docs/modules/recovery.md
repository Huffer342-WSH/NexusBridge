# qB 任务恢复

## 功能目标

当 qBittorrent 任务被意外删除、磁盘上的文件或目录仍然完整时，NexusBridge 可以重新找到原始 torrent、重建 qB 任务并映射到现有文件。恢复过程不会移动、复制或重命名磁盘文件。

该功能用于恢复“任务记录丢失但数据仍在”的场景，不用于修复损坏文件，也不保证把内容不完整的目录恢复为做种任务。

## 使用前提

- NexusBridge 能读取待恢复文件或目录。
- qBittorrent WebAPI 已连接，并允许添加、重命名、重新校验和启动任务。
- 使用数据库匹配前，torrent 文件大小签名必须完整。新保存的 torrent 会自动维护；手动重建仅用于修复缺失或解析失败的签名。
- 站点搜索和私站 torrent URL 需要对应站点配置及有效凭据。Cookie 只会通过统一请求策略发送给匹配的站点域名。
- 当前恢复要求 torrent 包含 v1 info hash；纯 v2 torrent 暂不支持。

## 操作入口

### 恢复单个文件或目录

1. 打开 WebUI 的“文件”页，浏览到仍保留在磁盘上的文件或目录。
2. 通过右键菜单选择“尝试恢复 qB 任务”。
3. 选择候选来源、可选站点和 qB 分类，然后先执行只读预览。
4. 只有唯一候选可以直接确认恢复；多候选必须由用户消歧，无候选时不会写入 qB。
5. 确认后等待添加、路径映射和强制校验完成。

单文件和目录都可以作为恢复目标。对于目录，匹配范围包括其全部普通文件；对于单文件，只比较该文件，不会把同目录其他文件计入集合。

### 扫描并批量恢复

“扫描丢失任务”会在当前目录下按指定深度查找未归属现有 qB 任务的条目。扫描是只读操作，默认递归深度为 1、最多评估 200 项；后端硬限制为深度 5、最多 500 项。

- 网页搜索默认关闭，此时只查询本地数据库。
- 用户启用网页搜索后，数据库没有候选的条目才继续搜索已配置站点。
- 批量恢复只提交扫描结果中的唯一候选。
- 后端串行执行，避免同时冲击 qB、SQLite 和站点。
- 相同路径或相同 torrent 在一个批次中只执行一次。
- 单项失败不终止后续项，结果分别显示成功、需要处理、失败和跳过。

## 候选来源与匹配规则

```text
文件或目录
  -> 文件大小多重集合
  -> 数据库大小索引 / 站点搜索 / 直接 torrent URL
  -> 解析 torrent 文件结构
  -> 完整大小集合一致
  -> 唯一恢复候选
```

支持以下来源：

| 来源 | 行为 |
| --- | --- |
| 本地数据库 | 使用完整大小多重集 SHA-256 签名缩小候选，再读取并解析内容寻址 torrent 文件。 |
| 站点网页 | 使用目标名称的多个搜索变体查询站点，按站点展示大小预筛后下载 torrent，并进行精确匹配。 |
| 数据库优先 | 先查询数据库；没有候选时才访问站点网页。 |
| 直接 URL | 下载用户提供的 torrent URL；匹配私站时通过统一入口携带该站允许的 Cookie。 |

最终判断不是只比较总大小，而是比较完整文件大小多重集合：

- 文件数量必须一致。
- 总大小必须一致。
- 每个文件大小及同一大小的重复次数必须一致。
- 文件名和相对路径用于优先建立映射，但不是内容真实性证明。

大小签名只负责缩小数据库候选范围。执行恢复前仍会重新读取磁盘、解析 torrent，并再次验证完整集合。目录批量扫描在一次遍历中为候选聚合大小，不保存本地目录树。当前不进行 piece SHA1 预校验，最终内容正确性由 qB 强制校验确认。

## qB 恢复流程

```text
唯一候选
  -> paused=true、skip_checking=true 添加
  -> savepath 设置为目标父目录
  -> root_folder=false、autoTMM=false
  -> renameFile 设置 qB 内部相对路径
  -> 设置或推断分类
  -> 手动触发 recheck，必要时重试
  -> 等待校验结束
  -> 100% 完成后开始做种
```

恢复添加时不会使用临时保存目录。NexusBridge 只修改 qB 任务内部的文件路径，使它们指向磁盘上已经存在的结构；磁盘文件本身保持不变。

第一次重新校验请求可能未进入 `checking` 状态，因此后端会等待并重试。只有任务在校验结束后仍为暂停完成状态、进度为 100% 且剩余字节为 0，才会自动启动做种。

## 分类自动推断

用户显式选择分类时直接使用该分类。未指定分类时，NexusBridge 会将最终恢复 `savepath` 与各 qB 分类的有效保存路径比较，并选择路径匹配且层级最深的分类。

有效保存路径按以下顺序计算：

1. 分类自身的 `savePath` 非空时直接使用。
2. 分类自身路径为空时，寻找最近的、`savePath` 非空的父分类，并在父路径后追加剩余分类层级。
3. 整条父分类链都没有路径时，读取 qB 的 `app/defaultSavePath`，再追加完整分类层级。

例如：

```text
PT          savePath = E:/.NSFW/PT
PT/ASMR     savePath = 空
```

则 `PT/ASMR` 的有效路径为：

```text
E:/.NSFW/PT/ASMR
```

如果 `PT` 也不存在或路径为空，而 qB 默认保存目录为 `E:/Downloads`，则有效路径为 `E:/Downloads/PT/ASMR`。路径比较会进行平台规范化；Windows 下不区分大小写。

若没有分类匹配，恢复执行才回退到 NexusBridge qB 配置中的全局默认分类；没有配置时保持无分类。

## 失败处理与安全边界

- 预览和扫描不会修改 qB 或磁盘文件。
- 候选不唯一时拒绝自动选择。
- qB 已有同 hash 任务时拒绝重复添加。
- 配置路径或分类失败时，只删除本次新增的 qB 任务，并使用 `deleteFiles=false` 保留文件。
- 校验失败或超时时，不重复添加 torrent，而是保留唯一暂停任务。
- 对校验失败任务，用户可以选择“仍然开始”或“删除任务，保留文件”。后者同样使用 `deleteFiles=false`。
- 批量恢复中的失败任务不会自动开始下载，也不会影响后续候选继续执行。

## 当前限制

- 站点搜索目前合并最多 5 个名称变体的第一页结果；多页搜索、中断续查和独立搜索记录持久化尚未完成。
- 不进行 piece SHA1 预校验，文件大小相同但内容不同的情况会在 qB 强制校验阶段失败。
- 纯 v2 torrent 暂不支持恢复。
- 恢复运行在 NexusBridge 所在机器的文件系统视角下；容器或远程部署必须确保路径对 NexusBridge 和 qB 都有一致含义。

## API 与代码入口

主要 HTTP 接口见 [HTTP API](../api.md)：

- `POST /api/files/browse`
- `POST /api/qb/recovery/preview`
- `POST /api/qb/recovery`
- `POST /api/qb/recovery/scan`
- `POST /api/qb/recovery/batch`
- `POST /api/qb/recovery/{hash}/action`
- `GET /api/qb/recovery/index`
- `POST /api/qb/recovery/index/rebuild`

| 模块 | 作用 |
| --- | --- |
| `internal/core/file_manager.go` | 浏览文件、标记现有 qB 归属并扫描候选。 |
| `internal/core/torrent_size_index.go` | 查询和手动重建大小签名。 |
| `internal/core/recovery.go` | 匹配 torrent、推断分类、添加任务、映射路径和校验。 |
| `internal/core/recovery_batch.go` | 串行执行扫描出的唯一候选。 |
| `internal/storage/torrent_files.go` | 保存内容寻址 torrent 文件元数据及完整大小签名。 |
| `internal/qbittorrent/client.go` | qB 认证、基础请求和默认保存路径查询。 |
| `internal/qbittorrent/torrents.go` | 添加、重命名、校验、启动和删除任务。 |

真实 qB 恢复测试的环境变量、安全边界和运行命令见 [测试文档](../testing.md)。
